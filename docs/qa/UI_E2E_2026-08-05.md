**Standardise on this, do not invent a fourth style.** The corpus supports exactly two back controls and they are used in roughly equal numbers (≈35 vs ≈36 of ~71 full-screen routes), so there is no incumbent to defer to — pick one and apply it everywhere. The recommendation is the **circled control**: a filled dark circle containing a left arrow, pinned top-left, since it is the only one that survives floating over hero imagery and illustrations (Programs and Library exercise detail both need that) and it is already the convention in the two densest lanes, Stats & Scores and You. Title treatment should ride with it as one header component rather than being chosen per screen (see row 163). Bottom sheets: **drag handle plus an explicit close-× top-right** — the handle alone is already the ~45-of-60 majority, and adding the × costs nothing while removing the guesswork; reserve a back-chevron in a sheet header exclusively for genuinely nested sheets, where it means "up one level", never "close". Dialogs are already consistent (text buttons, no icon dismiss) — leave them alone. And the error boundary must render a real Back/Close button before anything else here is worth doing (row 205).

## Notes on this sweep

**Note on RenderFlex overflow:** Flutter paints the yellow/black hazard stripe and the "RIGHT OVERFLOWED BY N PIXELS" banner **only in debug builds** — in release the overflowing content is silently clipped with no visual warning. That is exactly why this class survives unnoticed: a laid-out-too-wide row still ships, just without the stripe telling anyone. Screenshot sweeps of debug builds are currently the only place these surface.

**⚠ Tooling defect affecting every "does not scroll" finding.** The swipe helper
used to drive these sweeps (`scratchpad/sw.sh`) issued `cliclick m:` between
`dd:` and `du:`. `m:` posts a mouse-MOVE, not a mouse-DRAG — so Flutter never
received a scroll gesture and **no screen ever scrolled**, whether or not it was
scrollable. Any finding of the form "does not scroll" / "unreachable below the
fold" produced with it is unsafe until re-driven with the fixed helper
(`sw2.sh`, which uses `dm:`). Rows marked **SUSPECT — re-verify** above are the
known affected set. A sweep agent caught this after nearly filing a false CRIT
against a sheet that scrolls perfectly well; the tell was that the Home feed —
obviously scrollable — also refused to move.

Related: `xcrun simctl io screenshot` was observed lagging several actions
behind reality for a stretch. If a control looks dead, re-capture after a pause
before calling it broken.
