## UX verdict

### What makes it feel unreliable

Structurally the app is *not* confusing — navigation is conventional, flows are discoverable, and the copy is unusually good (written wait states, written empty states, a coach-mark that warns "Analyzing alone doesn't log it!"). Nobody gets lost. What they get is **uncertain** — the failure mode is "I did the thing and I'm not sure it worked." These are trust problems, not usability problems, and each maps to a row above:

1. **Colour has stopped meaning anything.** On a *single* screen the WARM-UP label is orange while the sliders and Next button are cyan. The log-meal action row is blue / green / orange / purple / pink — five colours in one row. The coach's workout card is a cyan→purple gradient with a purple Start. It reads as assembled by different teams. → **#15**, #13c
2. **Actions that don't visibly do anything.** Save 500s silently; Schedule quietly builds a *different* workout. Worse than an error — you cannot tell whether you or the app failed. → **#98**, **#99**, **#105**
3. **"Start" renders as "St/ar/t"** — the primary CTA on the coach card, unreadable. → **#94**
4. **The endless "Generating your workout…"** — no error, no retry, no explanation, core loop blocked. → **#104** (and #4, #92 for the earlier variants)
5. **Thirteen affordances to log one meal** (4 tabs + 5 buttons + 4 chips). For "I ate eggs," that is a lot of deciding. → **#107**
6. **Small credibility leaks:** "1 ITEM" next to "3 ITEMS" on the same row; "+1 moregrilled salmon steak"; "RPE 4" in a *beginner* program; "COMMERC…" truncated. → **#96**, **#100**, **#91**, **#108**

None of this is a redesign. One accent source of truth, surface failed writes as errors, fix the two broken buttons, kill the generate loop — that is the whole list.

> *"Zealova has a genuinely strong, opinionated visual identity — condensed all-caps display type on near-black, a hot-orange accent, dense-but-legible cards — and the onboarding is one of the better fitness onboardings I've seen: it earns each question with a 'why', shows a credible projection chart with citations, and lets you feel the product before it ever asks for money. Where it falls down is consistency and restraint."*

**Genuine strengths.** Onboarding justifies every question rather than just asking it. The projection screen is best-in-class — four labelled rates with the calorie cost of each, a plan-vs-solo chart with a real baseline, and actual citations. The equipment step handles a hard input well (location chips, camera shortcut, presets, search, plus a running confirmation). The paywall leads with a founder's reason instead of a fake countdown and shows a day-by-day charge timeline. Empty states are *written*, not defaulted. The workout action sheet is a model — every ambiguous action carries a plain-language sublabel, and Delete is the only red item. Menu analysis, when it works, is legitimately differentiated.

**The pattern behind most of the UX issues** is that individually reasonable decisions stack: five interstitials before a set, three tours plus a modal plus two banners on first run, nine entry points on the log sheet. Each is defensible alone; together they read as the app negotiating rather than working. The second pattern is *consistency* — an accent colour that changes between sessions, three pill colours implying a code that doesn't exist, and two different star treatments on one screen.

**If only three things get fixed for polish:** #22 (literal "Title/Subtitle" — the single most trust-damaging item), #15/#16 (unstable accent + a FAB that covers real controls), and #17 (day-one zero states framed as losses).

### The injury flow is the biggest untested risk

A code audit (not yet reproduced on device) found the safety chain holds on the
FIRST-generation path only, and leaks on five others. Storage is fine —
`limitations` survives signup into `users.active_injuries`, and
`exercise_safety_index_mat` is genuinely populated (2,192 tagged rows;
`knee_safe = false` on 689). But:

- **Regenerate has ZERO injury safety.** `/regenerate-stream` and `/regenerate`
  use `UserSafetyContext.normalized_injuries()`, which whitelists against a
  SINGULAR joint list while the app stores PLURAL ids (`knees`, `shoulders`,
  `wrists`, `ankles`, `hips`, `elbows`) — so **6 of 8 joints normalise to an
  empty list** and squats come straight back for a knee-injured user.
- **Quick Workout has no deterministic gate at all**, and its Title-Case
  singular chips (`Knee`) never match the stored plural ids, so profile injuries
  never pre-fill.
- An equipment **"finisher" is appended AFTER the terminal safety guard** with a
  no-op avoid set — it will hand a knee-injured user "Horizontal Leg Press"
  (`knee_safe = false`).
- The 11 muscle-area chips (Chest, Abs, Quads…) get a prompt sentence and **no
  filter** — `/generate-stream` computes `avoided_muscles` then discards it.
- The post-injury-change invalidation uses a bare-date `.eq` against the
  noon-anchored timestamptz and therefore matches **0 rows, always**.

Suggested device test: pick **Knees only** — 239 of 261 squat/lunge index rows
are `knee_safe = false` and there are 152 safe upper-leg alternatives, so a
correct result is unmistakable rather than merely a thinner workout.
