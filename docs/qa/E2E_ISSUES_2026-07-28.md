## 1. Fixed and verified in production

| 1.1 | **One Easy-tier set marked a whole workout complete.** `workout_logs.status` DEFAULTs to `'completed'`; migration 2256's `trg_sync_workout_completion` then flips `workouts.is_completed`. | 1.3 | **Fabricated 2000 kcal / 150 g nutrition targets.** `GET /nutrition/dynamic-targets` defaulted `prefs.get("target_calories") or 2000` when the user had no row and returned it as a *dynamic target*. ## 2. Open — found by driving the app

### 2.1 `HIGH` — Easy/Advanced toggle is broken four ways

Tapping **Advanced** in the active-workout top bar, mid-session:

1. **Exits the workout** back to the detail screen instead of switching in place.
2. **Restarts the session from the warm-up** — your place is lost.
3. **Never actually switches** — the toggle still reads "Easy".
4. **Never persists** — `users.workout_ui_mode` is still `NULL` and
   `workout_ui_mode_user_explicit` still `false` (verified by SQL).

The previously logged set *did* survive (Volume showed 250 kg = 25×10), so the
session state itself is intact; it's the mode switch that fails.

Related risk from the code audit, **not yet reproduced**: an Easy→Advanced swap
can double-write sets (Easy already POSTed each set; Advanced's finish
bulk-POSTs the full list with no dedup either side), and Advanced→Easy can
silently drop them (Advanced never POSTed; Easy's finish only PATCHes
`sets_json`). Worth a dedicated test once the toggle works at all.

### 2.2 `HIGH` — Menu scan invents a dish when the image fails

Scanning a 20-dish restaurant menu produced:

- a **blank white thumbnail** — the image never reached the analyzer;
- **"1 items · 1 section"**;
- one dish, **"Tandoori Chicken Half · $14.95 · 487 cal · Served with choice of
  one (1) Side"**, which appears **nowhere** on the scanned menu — rendered
  **twice** (Recommended + Mains).

Ruled out: `menu_scan_cache` is **empty (0 rows)**, so this is *not* a
cross-user cache collision. "Tandoori Chicken (Half)" is a real row in the app's
own override catalog (`migrations/1852_overrides_AE_uae.sql:1033`).

So a **failed upload yields a fabricated dish presented as a real menu item**,
with a price and macros, ready to log. That violates this repo's own rule
against silent fallbacks and invented data. A failed scan must fail visibly.

### 2.3 `MEDIUM` — Quick Generate writes `scheduled_date` at midnight UTC

Verified in production: the quick workout landed at `2026-07-28 00:00:00+00`,
while a normally generated one landed at `2026-07-29 17:00:00+00` (noon CDT,
the documented convention). Midnight UTC is **7pm the previous local day** for a
US user, so the workout mis-days in every local-day window.

### 2.5 Carried over from the code audit — not reproduced on device

Listed because they're serious if true, and because two of them would be felt by
every real user:

- **Editing an active program deletes weeks 2..N** and collapses each remaining
  week to a single workout.
- **A program that isn't 100 % complete permanently suppresses generation on its
  weekdays**, with no date expiry — and program progress never increments for
  tracked sessions, so the condition is effectively guaranteed.
- **Chat "Apply" writes to a phantom column.** `workouts` has `exercises_json`
  and **no `exercises`** (confirmed against live schema), yet
  `add_exercise_to_workout`, `replace_all_exercises` and `WorkoutModifier`'s
  add/remove/modify all send `{"exercises": [...]}` → 42703, whole update
  rejected, card still reports success. *The column-drift gate passes, so it
  does not cover writes made through the `db.update_workout` helper — a gap in
  the gate itself.*
- **Single-day regenerate has been broken at the DB level since 2026-05-03.**
- `POST /performance/drink-intake` can never succeed — the model requires
  `workout_log_id` and `drink_intake_logs` has no `workout_id` column.
- **Advanced-tier sets live only in RAM + SharedPreferences until Finish.** An
  OS kill mid-session loses the entire workout from the database.

## 3. UX review

*(Populated from a structured review of ~50 screenshots captured during the
walk; see §3.2. Strengths first, because they're real.)*

### 3.1 What works

- **The pre-auth quiz is genuinely good.** Progressive disclosure (picking
  "Intermediate" reveals sub-questions; picking "4 days" reveals a day picker),
  unselected days dim out, and every answer is echoed back later
  ("CONFIRMED FROM YOUR QUIZ: Male, 5'10", 181 lb").
- **Real personalisation, not template copy.** The blocker screen answers the
  *specific* obstacle you chose; the coach greets you by name; the home card
  quotes your actual logged calories.
- **Honest zero-states in most places** — "0 / 464 earned", "Workouts · 0 of 5",
  and the Stats tab's four component scores all read 0 rather than inventing
  progress.
- **Unit handling is correct** where it matters: toggling kg→lb converted both
  weights together (82 kg → 181 lb, 76 → 168) and rescaled the rulers.
- **Food logging is the strongest flow.** 648 kcal analysed in ~10 s, per-item
  breakdown that sums exactly (406+242 = 648; 27+7 = 34 P), correct local
  timestamp, and a genuinely useful line — "Protein's the long pole today."

### 3.2 Where it's confusing

Detailed findings are appended by the UX review pass. Recurring themes observed
directly during the walk:

- **Accent colour changes between screens** — orange (brand), blue (active
  workout), cyan (permissions, rest timer), purple (Apple Health), green
  (nutrition showcase). Some reads as deliberate colour-coding; the **stock cyan
  Material date picker** is clearly unthemed and looks like a different app.
- **Coach marks stack up.** Four separate tip overlays fire in the first minute
  after onboarding (home ×5, workout, nutrition, active workout ×3), each
  needing dismissal before the screen underneath is usable.
- **"Generating your workout…" shows fake progress.** The copy rotates through
  five strings on a 1.7 s timer regardless of actual state — so a stalled
  generation looks identical to a healthy one. (Root cause fixed in 1.2, but the
  cosmetic-progress pattern remains.)
- **The paywall's "Maybe later" is invisible for 4 s on iOS** by design. It is
  Play-policy-aware and deliberate, but a user who taps around in those 4 s
  finds no way out.
- **Menu scan gives no failure signal** — see 2.2. A blank thumbnail and a
  single unrelated dish look like a successful scan of a very short menu.

## 5. Process note

**Render logs caught three production failures before I did** — the readiness
500, the Imagen 502, and the `food_database` statement timeout. All three were
visible in the runtime log while the UI looked fine or merely empty. A live
error tail is now running for the rest of this pass; it should have been running
from the start. The lesson generalises: for this app the UI is a weak oracle,
because so many failures are fail-soft. **Watch the logs and the database, not
the screen.**
